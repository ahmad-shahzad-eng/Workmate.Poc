Conventions

  • Table prefixes stand in for module schemas (Hr_, Forms_, Proc_, Notif_, Ui_); in production each module gets its own SQL Server schema. ABP's own tables keep their Abp/OpenIddict names.
  • Every one of our tables has TenantId (entities implement ABP IMultiTenant); ABP's data filter adds TenantId = current company to every query. Companies are AbpTenants rows.
  • Ids are GUIDs (stored as TEXT in SQLite), generated sequentially by ABP.
  • People: an Hr_Employees row is the HR record; its UserId is the sign-in account in AbpUsers. Columns named …UserId on requests and tasks (SubmittedByUserId, Proc_TaskCandidates.UserId, CompletedByUserId) hold an Hr_Employees.Id, not an account id.
  • Two kinds of role: job roles (Hr_JobRoles, HR data used for routing) and the permission role Workmate.CompanyAdmin (AbpRoles, used for access).
  • ABP columns on aggregate roots: ExtraProperties, ConcurrencyStamp (optimistic locking), and on audited entities CreationTime, CreatorId, LastModification*, and soft delete (IsDeleted, DeleterId, DeletionTime). The table reference lists them separately.
  • Relationships are by id, not database foreign keys. The links below are enforced by the application; the PoC declares no FK constraints.
  • Nothing is shared across the two files: our tables store Elsa ids as plain strings, and only ElsaWorkflowGateway reads Elsa's side.

Answers: Forms_Submissions.DataJson

Flat object of field key → string. Booleans are "true"/"false", numbers use the invariant culture, dates are yyyy-MM-dd. Both renderers produce exactly this format.

{ "leaveType": "Annual", "startDate": "2026-11-01", "endDate": "2026-11-03", "days": "3", "reason": "Family trip" }

For each reportable field one row goes to Forms_SubmissionValues: number → NumberValue, date → DateValue, checkbox → BoolValue, everything else → StringValue.

Designed workflow: Proc_ApprovalWorkflowVersions.StepsJson and FallbackRule

PropertyValues
steps[].titleStep name shown on the task
steps[].approverTypeline-manager, manager-of-manager, department-head, role, user
steps[].roleRequired when approverType = role; a name from Hr_JobRoles
steps[].userIdRequired when approverType = user; an Hr_Employees.Id of the same company

{ "steps": [
  { "title": "Manager approval", "approverType": "line-manager", "onReject": "end" },
  { "title": "Finance review",   "approverType": "role", "role": "Finance", "onReject": "back-to-previous" },
  { "title": "HR sign-off",      "approverType": "user", "userId": "5011337f-…", "onReject": "end" }
] }
FallbackRule = "role:HR"

On publish, ApprovalWorkflowGraphBuilder turns this into an Elsa flowchart (one HumanTask per step, then CompleteProcess) and the gateway publishes it to WorkflowDefinitions.

Assignment rules: Proc_Tasks.AssignmentRule and FallbackRule

line-manager, manager-of-manager, department-head, role:{Role}, user:{EmployeeId}. Resolved at run time by AssignmentResolver into Proc_TaskCandidates rows; the submitter and deactivated people are never candidates. A task's FallbackRule is copied from the workflow when the task is created (null on the two code-defined workflows means role:HR).

Email templates: Notif_EmailTemplates.Subject and Body

Plain text with placeholders, checked on save against an allow-list (sandboxed Scriban): {{ request.title }}, {{ request.number }}, {{ request.status }}, {{ initiator.name }}, {{ approver.name }}, {{ step.title }}, {{ comment }}, {{ link }}, {{ company.name }}, {{ fields.<key> }} (form templates only), and {{ if … }} … {{ else }} … {{ end }}. Notif_EmailMessages stores the rendered result (TextBody, and HtmlBody in a fixed layout using the company's brand colour).

Branding: Ui_CompanyBranding

BrandColor is #rrggbb in lower case. Logo is the image bytes, typed by LogoContentType (decided from the bytes, not the upload); LogoVersion goes up on every change and is part of the logo URL /api/poc/branding/logo/{TenantId}?v={LogoVersion}.
