**Gate actually run, not just planned** — six real bugs surfaced only by starting the app and calling `/connect/token` for real, each fixed in `WorkmatePocModule.cs`/`Data/DemoDataSeeder.cs`:
1. `AbpPermissionManagementDomainModule`'s own startup hook tried to sync `WorkmatePermissionDefinitionProvider`'s permissions before the tables existed (`EnsureCreatedAsync` ran in `OnApplicationInitializationAsync`, which — being the most-dependent module — runs *last* in that phase). Fixed by moving `EnsureCreatedAsync` into `OnPreApplicationInitializationAsync`, a separate, earlier full pass across every module.
2. `AbpOpenIddictAspNetCoreModule` transitively pulls in the ABP MVC UI theme/bundling modules (for its own Razor views), which 500 every request when `wwwroot/libs` doesn't exist — we don't use that theme at all. Fixed with `Configure<AbpMvcLibsOptions>(o => o.CheckLibs = false)`.
3. `AbpOpenIddictAspNetCoreModule` depends on `AbpIdentityDomainModule` but not `AbpIdentityAspNetCoreModule`, so `SignInManager<IdentityUser>` (which `TokenController` needs) was never registered. Added the missing module + package.
4. OpenIddict refuses `/connect/token` over plain HTTP by default (ID2083) — this app has no HTTPS story for local dev. Fixed with `PreConfigure<OpenIddictServerBuilder>(b => b.UseAspNetCore().DisableTransportSecurityRequirement())`.
5. SQLite only allows one writer; `TokenController`'s own security-log write opened a nested unit of work while the outer per-request one was still open, throwing "database is locked" on every successful sign-in. Fixed with `Configure<AbpUnitOfWorkDefaultOptions>(o => o.TransactionBehavior = UnitOfWorkTransactionBehavior.Disabled)` — the exact setting ABP's own template uses for SQLite, confirmed needed by hitting the error for real, not assumed up front.
6. Disabling `AbpIdentityAspNetCoreModule`'s own cookie-scheme setup (needed per #3's neighbor concern) left no `DefaultChallengeScheme` registered at all, so a 403 turned into an unhandled 500 ("There was no DefaultChallengeScheme found"). Fixed with an explicit `AddAuthentication(o => { o.DefaultScheme = o.DefaultChallengeScheme = OpenIddictValidationAspNetCoreDefaults.AuthenticationScheme; })`.

After all six fixes: `POST /connect/token` issues a real JWT with the correct `tenantid` claim; `GET /api/poc/forms` returns only the signed-in user's own tenant's forms; `[Authorize(WorkmatePermissions.FormsDesign)]` correctly 403s a non-admin (Sara), 200s a `Workmate.CompanyAdmin` (Khalid), and 401s an anonymous caller; an ordinary employee's forged `X-Act-As-Tenant` header pointed at the other tenant is silently ignored (still sees only her own company's forms); the vendor admin (genuine host user, no tenant) successfully uses that same header to view a specific company's data. Also discovered along the way: the tenant's display name went into `Tenant.Name` directly (not a separate `DisplayName`) since the fixed-GUID approach from plan.md turned out to be impossible — `Tenant`'s constructor is `protected internal` to ABP's own module, so `TenantManager.CreateAsync` always generates a fresh id; demo.py and the UI now look tenants up by name instead (ABP's tenant resolution already supports this natively, confirmed via source).

**Seventh bug, found verifying US1's "vendor admin designs for any company" (7p):** granting `FormsDesign` to the vendor admin's user id, per-tenant, inside `_currentTenant.Change(tenant.Id)` (so the `PermissionGrant` row's `TenantId` matched — `PermissionGrant` implements `IMultiTenant` too, confirmed from source) still 403'd. Root cause, found by reading `PermissionChecker.IsGrantedAsync`: it gates `MultiTenancySide` on `claimsPrincipal.GetMultiTenancySide()` (literally `principal.FindTenantId().HasValue`, i.e. the **token's own** tenant claim), never on the ambient `ICurrentTenant.Id` our resolver changes — so a host-authenticated principal is categorically ineligible for a `MultiTenancySides.Tenant`-only permission, no grant can ever satisfy it. Fixed by declaring `FormsDesign`/`RoutingManage`/`WorkflowsDesign` as `MultiTenancySides.Both` in `WorkmatePermissionDefinitionProvider`; `TenantAdminRoleSeeder.EnsureCompanyAdminRoleAsync` now takes an optional `alsoGrantToUserId` so both `DemoDataSeeder` (existing tenants) and `TenantOnboardingAppService` (every tenant created afterward) grant the vendor admin those three permissions in that specific tenant automatically.

**Full demo.py suite (67/67) + restart check (3/3 before, 11/11 after) pass** after all seven fixes — the complete rewrite to real bearer-token sign-in (steps 1–11, restart check) runs clean end to end.

## Dependencies & Execution Order

T001 → T002 → **Phase 2 (T003–T012, mostly sequential — see per-task notes; T003/T004/T005/T007/T010 can run in parallel with each other)** → **US1 (T013–T016) ∥ US2 (T017–T019)** → US3 (T020–T024) → T025–T026.

US1 and US2 have no code dependency on each other and can be built in either order once Phase 2's gate passes. US3's code (T020–T023) is independent of both, but its verification task (T024) needs `demo.py` already sending bearer tokens (T018) — so implement US3 after US2 in practice even though nothing in US3's code imports anything from US2. Phase 2 cannot be parallelized with Setup or split across stories: every existing feature (forms, submissions, tasks, routing) resolves "who is signed in" through `CurrentEmployeeProvider`, which T008–T012 rewrite — nothing else in the app runs correctly until the whole phase lands together.

## Implementation Strategy

**MVP = Phase 2 (Foundational) alone**, verified by curl, not the UI or `demo.py` — proves real sign-in works end to end for one seeded user before touching anything user-facing. From there, US1 and US2 are each independently demoable; US3 is the cleanup that removes the last trace of `IsAdmin`. Given how much of this feature is infrastructure (not a thin layer over existing code, unlike most prior phases), expect Phase 2 to be the majority of the effort — that's consistent with its scope (replacing the entire identity/tenant/permission substrate the whole app already depends on).
